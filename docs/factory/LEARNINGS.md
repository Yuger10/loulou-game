# Learnings : chaque correction devient un check

Boucle d'amélioration du playbook cothon (7.3). Après chaque correction d'Amrou ou incident d'un agent : trois lignes (ce qui s'est passé, pourquoi, ce qui l'empêche désormais), puis un check qui rend l'erreur impossible. Une ligne dans `AGENTS.md` seule ne suffit pas : la colonne « Check » dit si l'erreur est vraiment bloquée.

| Date | Ce qui s'est passé | Pourquoi | Ce qui l'empêche | Check |
|---|---|---|---|---|
| 2026-11-21 | L'agent a coupé 5 règles de lint pour livrer vite ; Amrou : « je préfère corriger proprement » | Désactiver est plus rapide que corriger | Convention « corriger plutôt que désactiver » dans `AGENTS.md`, track `lint-regles-completes` | ⏳ la track réactive les règles |
| 2026-11-22 | « Version 66 » affichée alors que du code changé était en ligne | La version n'augmentait qu'avec une track | Versions 66.x (ADR 0005), `bun run release` | ✅ `test/update.test.js` (version = cache) |
| 2026-11-22 | Deux vérifications du test de fumée finissaient par `\|\| true` et passaient toujours (depuis la v11) | Test écrit vite, jamais relu | Lint sur `test/` | ✅ oxlint (`no-unused-vars` les a révélées) |
| 2026-11-22 | Un appel `bellSVG(m, i)` n'avait pas suivi le retrait du paramètre `i` (par l'agent, étape oxlint) | Aucun typecheck à l'époque | TypeScript en vérification du JS (ADR 0003) | ✅ `tsc` dans `check`, la CI et le hook de l'agent |
| 2026-11-22 | Un test des coccinelles échouait 1 fois sur 6, impossible à reproduire | `Math.random` direct, sans graine | Une seule source de hasard, graine rejouable | ✅ oxlint `no-restricted-properties`, `TEST_SEED` affiché par le lanceur |
| 2026-11-22 | Une écriture de sauvegarde ratée passait en silence (`catch {}` vide) | Les blocs vides n'étaient pas interdits | `storageWrite`, message à l'enfant, carte parents | ✅ oxlint `no-empty` et `localStorage.setItem` interdit, `test/stockage.test.js` |
| 2026-11-22 | L'agent a voulu annuler une expérience avec `git checkout` alors que ses modifications n'étaient pas commitées (bloqué par le garde-fou) | Habitude d'annuler par checkout | Commiter avant toute expérience qui s'annule | ⏳ consigne, pas de check |
| 2026-11-22 | Une PR empilée visait encore la branche de la PR précédente au moment du merge (#52) | GitHub ne la réoriente pas tout seul si la branche reste | Réorienter vers `main` avant de merger une PR empilée | ⏳ consigne, pas de check |
| 2026-11-22 | L'agent a voulu poser lui-même l'étiquette `human:approved` sur sa PR, sur délégation (refusé par le garde-fou) | Confusion entre « vérifier » et « approuver » | L'étiquette est posée par un humain, jamais par l'agent, même sur délégation (`AGENTS.md`) | ✅ garde-fou de l'agent ; la CI exige l'étiquette |
| 2026-11-22 | « ok go » et « Oui » n'ont pas suffi à autoriser un merge | Un merge exige un ordre explicite | Demander « merge la PR N » | ✅ garde-fou de l'agent |
| 2026-11-22 | Une PR qui mélangeait du code et une ligne de CI (`.github/`) est restée bloquée par le garde des zones sensibles (#61) | La zone protégée bloque toute la PR | Toute modification de zone protégée dans sa propre PR | ✅ le garde la sépare de fait ; consigne dans le REX cothon |
| 2026-11-22 | La garde des ressources a refusé une commande qui citait seulement une commande dangereuse dans un texte (description de PR) | Le hook lit le texte brut de la commande | La garde lit la ligne comme le shell : commande par commande, hors guillemets et heredocs (le même défaut liait aussi deux commandes d'une même ligne) | ✅ `guard-resources.js --selftest` (les 3 faux positifs sont des cas) |
| 2026-11-22 | `main` était rouge depuis le merge de la #64 (puis de la #69), sans que personne le voie : l'agent ne regardait que la CI des PR | La CI d'une PR teste la PR, pas `main` après les merges suivants | Après chaque merge, vérifier le run de `main` (`gh run list --branch main`) | ⏳ consigne ; à automatiser si ça revient |
| 2026-11-22 | Un test de fumée (❤️ sur le personnage aidé) échouait avec certaines graines : une mission du jour tirée au hasard sur ce personnage affiche 📜 avant ❤️ | Le test supposait l'absence de mission | Le test termine les missions « personnage » avant de vérifier ; 12 graines balayées, toutes vertes | ✅ graine rejouable (`TEST_SEED=34348`) |
| 2026-11-22 | La place des décorations déplacées par l'enfant était perdue au redémarrage, depuis leur introduction | `load()` filtre sur `DEFAULT_STATE`, et une copie de cette liste écrite à la main avait oublié 3 champs ; aucun test ne rechargeait le jeu | Une seule liste (`freshState()`), et le type `GameState` force à la garder complète | ✅ `test/redemarrage.test.js` ; TypeScript strict sur `entities` (c'est lui qui l'a révélé) |
| 2026-11-22 | L'avatar d'une sauvegarde importée s'insérait tel quel dans le HTML (aperçu de restauration, puis à chaque lancement) : un fichier piégé pouvait exécuter du code | Seul le prénom avait une porte d'entrée (`cleanName`) ; `fixAvatar` ne corrigeait que deux anciens emoji | `fixAvatar` valide tout avatar chargé ou importé ; la date d'une sauvegarde est vérifiée aussi | ✅ `test/avatars.test.js` ; révélé par TypeScript strict (lot 4) |
| 2026-11-22 | L'espace parents plantait sur la partie d'un autre joueur venue d'une sauvegarde importée, et y insérait ses compteurs tels quels ; une activité de pause inconnue faisait planter le rappel « Hier, … » | L'espace parents lisait le JSON brut, sans la porte de `load()` ; les compteurs n'étaient jamais vérifiés | Une seule porte de lecture, `readSave()`, qui remet en forme suivi et journal ; `rest` ignore une activité inconnue | ✅ `test/parties-importees.test.js` ; révélé par TypeScript strict (lot 4) |
| 2026-11-22 | L'agent a d'abord pris un échec de `verify` pour un test instable, parce que `check` passait ensuite : c'était le holdout (un champ ajouté à une partie réelle) | Lire le verdict final au lieu de l'étape en échec | Avant de conclure « instable », lire quelle étape échoue (`check` ne lance pas le holdout) | ⏳ consigne |
| 2026-11-22 | En multijoueur, une paire ratée au jeu de mémoire ou le temps écoulé bloquaient le tour (erreur JavaScript, la main ne passait pas) | `wrongFeedback` supposait toujours un bouton fautif ; aucun test du multijoueur hors des boutons | `wrongFeedback(null)` : effets visuels seulement s'il y a un bouton, la main passe toujours | ✅ `test/multijoueur.test.js` ; révélé par TypeScript strict (lot 3a) |

Les lignes ⏳ sont des candidates : si elles reviennent, elles deviennent un check (script, test ou règle).
