# Retour d'expérience : cothon 0.1.0 installé sur loulou-game

> **Pour** la session qui maintient cothon (`~/Desktop/dev/cothon`). **De** la session qui l'a installé sur `loulou-game`, du 21 au 22 novembre 2026 (PR #45 à #64). Chaque point dit ce qui s'est passé, avec la mesure ou le fichier qui le prouve, et une proposition. Vérifié contre cothon 0.3.0 : les points marqués « encore vrai en 0.3.0 » n'y sont pas traités.

## Le projet, pour situer
Jeu éducatif PWA pour une enfant, JavaScript vanilla en modules ES **servis sans build** (GitHub Pages depuis `main`), 167 modules, 1 500 vérifications de tests jsdom, un développeur et plusieurs sessions d'agents en parallèle. Profil cothon : « jeu HTML » et « petit projet ».

## Ce qui a très bien marché
1. **Phase 0, l'audit.** Il a trouvé 5 vrais anti-patterns, tous corrigés depuis : prénoms insérés sans échappement (y compris depuis une sauvegarde importée), `Math.random` direct (cause d'un test qui échouait 1 fois sur 6), `catch {}` vides qui **cachaient des sauvegardes ratées**, délais copiés-collés dans 33 mini-jeux, rituel de livraison à la main.
2. **« Un anti-pattern = une PR qui le supprime partout et ajoute la règle. »** La règle la plus rentable du playbook. Chaque fois, la règle native d'oxlint suffisait (`no-restricted-properties` pour `Math.random` et `localStorage.setItem`, `no-empty`) : aucune règle custom en plugin JS n'a été nécessaire.
3. **Le lint révèle de vrais défauts, pas seulement du style** : deux vérifications du test de fumée finissaient par `|| true` et passaient toujours depuis des semaines ; `no-console` a révélé qu'une sauvegarde illisible faisait repartir de zéro en silence.
4. **TypeScript, même sur un projet JavaScript**, a attrapé une incohérence laissée par un agent (un appel qui n'avait pas suivi le retrait d'un paramètre).
5. **Les mesures** : tests 108 s → 18 s (parallèle), lint 33 ms, types 93 ms, hook de l'agent 211 ms (format, lint, types), CI 66 s en médiane. Les budgets du playbook ont guidé chaque décision.
6. **« Agnostique en philosophie, opinionné en outils »** : le propriétaire a d'abord choisi pnpm et Biome, puis s'est aligné sur la référence en lisant le playbook. La règle « un écart passe par un ADR » a produit 4 ADR utiles (`docs/adr/0003` à `0006`).

## Frictions et propositions

### Playbook
1. **Deux playbooks en circulation.** Une copie ancienne (`~/Desktop/dev/factory/software-factory-playbook.md` : pnpm, Biome) a été suivie pour l'audit, puis le plugin (bun, oxlint) l'a contredite. Le propriétaire a dû changer deux réponses. *Proposition :* un numéro de version en tête du playbook, et supprimer ou marquer « obsolète » les copies hors du dépôt cothon.
2. **La checklist finale (section 10) ignore les profils.** Pour un « petit projet », la section 8 dit « phases 0 à 2 seulement », mais la checklist liste 19 points dont pipeline, Docker, evals, étape 5. Le propriétaire a demandé « qu'est-ce qu'on garde, qu'est-ce qu'on ignore ». *Proposition :* une checklist par profil, ou une colonne « profil » dans la section 10. Notre tri est dans `docs/adr/0006-ecarts-playbook-cothon.md`.
3. **Pas de section sur les versions et la livraison.** Le projet a eu besoin de versions 66.1, 66.2 pour les livraisons sans fonctionnalité (outillage, corrections), sinon le numéro affiché ne bougeait pas alors que le code changeait en production. Nous avons écrit `bun run release patch|track "résumé"` (ADR 0005). *Proposition :* une courte section « version et livraison » (un numéro par livraison, un script de livraison).
4. **Projets sans TypeScript : aucun chemin.** Le playbook et `migrating-to-tsgo` supposent TypeScript 5 ou 6. Pour du JavaScript, la voie a été `tsc` 7 en `checkJs` avec JSDoc, sans build. Mesures : 284 erreurs en mode souple, dont 260 dues au DOM ; un seul fichier `types/dom.d.ts` (le jeu interroge son propre HTML : `querySelector` renvoie `HTMLElement`) en fait tomber 200. *Proposition :* une branche « projet JavaScript » dans `migrating-to-tsgo` (ou un skill `adding-checkjs`), avec ce fichier de types.
5. **« `suspicious` en erreur » sans garde-fou sur la compatibilité navigateur.** `unicorn/no-array-sort` impose `toSorted` (Safari 16+) : appliquée telle quelle, elle aurait cassé le jeu sur les vieilles tablettes. Le propriétaire veut un jeu « qui fonctionne partout ». *Proposition :* à l'audit, noter la cible navigateur (ou runtime) et la vérifier avant d'activer les règles qui imposent des API récentes. Encore vrai en 0.3.0.

### Skills
6. **`auditing-tool-speed` : `bunx` fausse les mesures.** Mesurer `bunx oxlint` donne 140 à 180 ms, presque tout en lancement de `bunx` ; le binaire local fait 33 ms. *Proposition :* mesurer `node_modules/.bin/<outil>` (ou `hyperfine -N`). Et `hyperfine` refuse un `|` sans `--shell=default` (erreur explicite, mais la commande d'exemple du skill ne le prévoit pas).
7. **`migrating-to-oxlint` : `-D suspicious` en ligne de commande ne donnait aucun signalement de plus, alors que la même catégorie dans `.oxlintrc.json` en a donné plus de 300** (oxlint 1.94.0). Mesurer avec la CLI a sous-estimé l'effort. *Proposition :* mesurer avec un fichier de config temporaire.
8. **`migrating-to-oxlint` : déclarer `"plugins"` change les règles actives.** Pour activer `import/no-cycle`, nous avons listé les plugins ; cela a activé `import/no-unassigned-import`, qui interdit les imports à effet, alors que c'est l'architecture du projet (`main.js` charge les slices ainsi, ADR 0002). *Proposition :* le signaler dans le skill.
9. **`migrating-to-oxlint` : certaines règles `suspicious` heurtent des contraintes de projet.** `consistent-function-scoping` voulait sortir 50 fonctions internes au niveau du module, ce qui créait des noms en double (5 `key`, 4 `ok`), interdits par notre test d'architecture (les tests lisent le jeu par nom). `prefer-add-event-listener` (195 cas) heurte l'idiome `el.onclick =`, qui évite les doublons de handlers à chaque rendu : le projet va passer par un helper. *Proposition :* un tableau « règle, cas, décision, raison » dans le gabarit de `SPEED.md`, qui a été notre meilleur outil de discussion avec le propriétaire.
10. **`migrating-to-oxfmt` : le CSS aussi.** oxfmt formate le CSS et y applique `singleQuote` (`[data-world='x']`) : 7 tests qui lisaient le CSS à l'octet près ont cassé. Correctif : `"overrides": [{ "files": ["*.css"], "options": { "singleQuote": false } }]`, et `ignorePatterns` pour les fichiers générés (`sw.js`, `index.html`). Encore vrai en 0.3.0. *Proposition :* l'ajouter au skill, et mesurer avant de décider **la taille du diff et le poids servi** pour un projet sans build : ici +44 % de lignes (style compact vers style Prettier), +5 % d'octets servis (+1,7 % en gzip). Le propriétaire a choisi en connaissance de cause.
11. **`wiring-fast-feedback` : lefthook 2.x n'a plus de `postinstall`.** Le skill dit d'ajouter lefthook à `trustedDependencies` « car son postinstall installe les hooks » : avec lefthook 2.2.2, `bun pm untrusted` ne liste rien et aucun hook n'est installé. Correctif : `"prepare": "lefthook install"` dans `package.json`. **Encore vrai en 0.3.0** (ligne 53 du skill). Le script `lint-edited-file.sh` a marché tel quel ; nous y avons ajouté `tsc -p .` (211 ms en tout, dans le budget).
12. **`speeding-up-ci` : plus simple que le squelette.** `oven-sh/setup-bun` v2.2 a son propre cache : `actions/cache` et le workflow réutilisable `_task.yml` étaient superflus pour un seul paquet. Un seul `ci.yml` avec 3 jobs et `ci-ok` suffit.
13. **Il manque un skill pour paralléliser des tests qui ne sont ni Vitest ni `bun test`.** Notre lanceur (`test/tools/run.js`, 90 lignes) trouve les suites seul, les lance en parallèle, découpe une suite lente (`// @shards N`), et rend le hasard rejouable (`TEST_SEED`, graine affichée en cas d'échec). Gain : 108 s → 18 s, sans réécrire 5 500 lignes de tests. *Proposition :* un skill `parallelizing-tests` générique.

### Phase 2 : le garde des zones sensibles
14. **L'amorçage.** La PR qui crée le garde et les tests holdout est bloquée par le garde lui-même. Ni le playbook ni les skills ne le disent ; il faut créer les étiquettes (`needs-human:sensitive`, `human:approved`) avant.
15. **Ordre des étapes du garde.** Notre première version échouait **avant** de poser l'étiquette `needs-human:sensitive`, justement dans le cas où elle compte le plus. Correctif : calculer, étiqueter, puis échouer.
16. **L'étiquette d'approbation est humaine, et le garde-fou de l'agent le fait respecter.** Même sur délégation explicite (« fais les tests toi-même »), le garde-fou de Claude Code a refusé que l'agent pose `human:approved` sur sa propre PR, et il avait raison. La bonne pratique trouvée : **mettre toute modification de zone protégée dans sa propre PR**, pour qu'elle n'en bloque pas d'autres. *Proposition :* l'écrire dans le playbook (5.4).
17. **Holdout « exclu du contexte de l'agent » : impossible en local.** La CI le protège à la place. Pour un projet sans base de données, des **sauvegardes réelles figées** (`test/holdout/sauvegardes/*.json`) remplacent la base éphémère : une migration qui perd des données fait échouer le holdout (testé par mutation).

### Conduite de l'agent
18. **Un merge exige une phrase explicite.** « ok go » et « Oui » ont été refusés par le garde-fou ; « merge la PR N » passe. *Proposition :* le dire dans le playbook (section 1), pour que l'agent demande la bonne formule au lieu de tenter.
19. **Toujours commiter avant une expérience qui s'annule** (`git checkout` pour annuler un test de mutation) : le garde-fou a bloqué une annulation qui aurait effacé des modifications non commitées.
20. **PR empilées** : GitHub ne réoriente pas une PR empilée vers `main` si la branche de base reste ; il faut le faire avant de merger, sinon le merge va dans la mauvaise branche.
